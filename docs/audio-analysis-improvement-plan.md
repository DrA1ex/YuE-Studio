# Audio analysis: evidence and recommended redesign

Research date: 2026-09-21. Scope: identify and implement a more effective and robust analysis path; no model download, UI automation or real-song inference is used for validation.

## Implemented in the current checkout

- Melody, lyrics, genre and style are independent persistent stages keyed by the normalized audio SHA-256. JSON artifacts are atomic, inspectable and reusable only when model revisions and decoding options match; failed stages leave a failure record.
- Whisper uses the real `input_features` and attention mask through the sequential path, with segment timestamps and single-beam decoding as the stable primary lyric result. Word alignment remains guarded recovery code and cannot discard recognized text. Per-segment timing diagnostics are saved with the import.
- Genre output retains five ranked candidates and per-excerpt rankings. Close or weak evidence is shown as a hybrid or `Mixed / uncertain` suggestion instead of an uncalibrated top-1 claim.
- CLAP style output can retain multiple independently supported descriptors per category and preserves support across excerpts. The app maps technical warnings to short user-facing guidance while keeping raw metadata and logs.
- The app refreshes cover-engine readiness from disk when Settings opens and exposes the resumable analysis cache as a separate removable storage target. Existing lyric text is not overwritten automatically when the user has already entered text.
- Verification remains synthetic: Python regression tests and native Swift tests only. No release or DMG was generated by this implementation pass.

The accelerated MLX transcription worker and vocal-boundary segmentation are now integrated as optional, separately installed stages with fallback. The current structure stage is a lightweight spectral-repetition/tempo analyzer; a learned All-In-One-style semantic structure model remains optional future work because it needs a separate runtime manifest and parity benchmark.

## Verified local findings

- Host memory: 16 GiB, Apple Silicon (Mac14,10). Performance has not been benchmarked for the proposed engines.
- Current Whisper runs on CPU in FP32 with eager attention, three beams and word alignment, inside the SheetSage environment pinned to Transformers 4.45.2 (`tools/transcribe_cover.py`). This couples two unrelated engines and makes upgrades risky. Eager attention is needed by the current alignment route but costs attention memory; three beams are not demonstrated to improve this user's singing transcription.
- The latest saved import analysis selected Rock with averaged classifier score 0.4168, versus Hiphop 0.3139. These are model scores, not calibrated probabilities of correctness. The code unconditionally displays the first label; it has no disagreement/abstention policy.
- The genre model was trained on GTZAN: 1,000 30-second tracks in ten genres. It cannot describe production, instruments, subgenres, or hybrid styles outside that label set [1].
- CLAP selected only mood and pace in that saved analysis. The code allows just one descriptor per category, including instruments, from a small fixed vocabulary. It averages three fixed-position 10-second excerpts; intro/outro material can dominate a short track, and disagreements are lost. The cosine thresholds and margins are heuristics, not calibrated evidence of accuracy.
- Saved transcription has 44 segment chunks and reports segment fallback. This confirms failure to retain word alignment, but the saved metadata does not identify whether timestamp length, monotonicity, finiteness or word decoding caused the fallback. The synthetic short-array regression establishes a failure mechanism, not the exact cause in this song.
- Word timestamps from generated segments are concatenated and validated globally. The next diagnostic must inspect token/timestamp correspondence and offsets per segment; harmless segment-boundary behavior must not invalidate all words. Do not pad fabricated timestamps just to pass validation.
- Intro, bridge and outro labels currently depend partly on token counts and position (`tools/lyrics_structure.py`), not acoustic evidence. Repeated text is helpful evidence but insufficient to distinguish verse, hook, chorus and pre-chorus.
- The app normalizes input to mono before all analysis. A stem separator should instead receive preserved stereo; create task-specific resampled derivatives afterwards.
- Every Analyze run repeats melody, lyrics and style stages. On process failure the temporary directory is removed, even when the score stage succeeded. There is no persistent per-stage cache or resumable partial analysis.

## Recommended implementation

### 1. Separate engine lifecycles and preserve evidence

Keep the current SheetSage environment pinned. Give lyric recognition/separation/structure their own versioned runtime or bundled native worker. Model manifests must track repository revision, required files and installation state per component, not just installed-vN markers. Validate an installation before marking it ready; preserve the last working engine during upgrades.

Represent melody, lyrics, alignment, structure and style as independent stages with ready/partial/failed/cancelled states. Atomically save completed outputs under a cache key including audio content hash, preprocessing revision, model revisions and options. Retry only failed stages. A word alignment failure must not discard text, and a style failure must not discard melody. Do not overwrite user-edited lyrics/style without an explicit Apply action.

Record diagnostic data per segment: index, start/end, token count, timestamp count, non-finite values, boundary overlaps, requested/actual decoding mode, elapsed time and peak memory. Keep verbose tracebacks in the log; show one short user-facing status with actionable recovery.

### 2. Improve lyric recognition before formatting

Use source separation to identify singing activity and phrase boundaries. HTDemucs is the baseline candidate; share its stems with acoustic structure analysis so it runs once. Preserve stereo for separation and original audio for comparison.

Do not assume isolated vocals always produce better lyrics. The ICME 2025 study found that naive long-form transcription of separated vocals can degrade quality, while using separation to determine vocal segment boundaries improved results on its benchmarks [2]. Implement the segmentation strategy first, retaining original-mix and vocal inputs as explicit alternatives. Use contiguous bounded windows with padding and overlap, maintain global offsets, and avoid speech-only VAD that clips sustained singing. Repetition alone is not a hallucination: choruses legitimately repeat.

For Apple Silicon, the first backend to evaluate is `mlx-whisper`, with turbo as the fast profile and full large-v3 as an optional accuracy candidate [3]. It supports arrays and local model directories, allowing AVFoundation PCM decoding without a global FFmpeg requirement. This is a platform-fit recommendation, not evidence of lower WER. Its current beam decoder is unimplemented: do not carry `num_beams=3` across blindly. Compare decoding settings deliberately.

`whisper.cpp` is the alternative if a bundled native worker is preferred: it supports Apple acceleration and avoids the Python/Transformers dependency coupling [4]. Its word-timing features still require validation and must not be treated as a guaranteed alignment fix.

Recognize text first; run word alignment as an optional second stage. Keep segment timing available independently. Retry only low-quality spans at most once using an alternate input/model; scores can prioritize review but do not establish correctness. Record uncertain spans rather than rewriting them into plausible lyrics with an LLM. Preserve ad-libs and backing-vocal text already recognized.

### 3. Determine song structure from audio

Use a music structure model to estimate beats, downbeats and functional boundaries. Assign recognized words/lines by overlap with those boundaries; use lyric repetitions only as corroboration. Unknown or conflicting sections should remain generic rather than inventing bridges.

All-In-One is directly relevant: its outputs include BPM, beats and labeled sections [5]. The Apple-specific `all-in-one-mlx` port is a promising candidate, but is marked beta and needs numerical/parity and packaging validation [6]. Its declared NumPy >=1.26 conflicts with the current cover runtime's NumPy 1.24.3, reinforcing runtime separation. It also brings MLX/NATTEN-MLX/Demucs-MLX dependencies. Check minimum macOS support of the selected wheels against the app's macOS 14 requirement before adopting them.

Do not choose `all-in-one-infer` expecting MPS acceleration: its current documentation explicitly rejects MPS [7]. CPU remains an option, not the preferred accelerated Mac path. A lighter acoustic repetition/boundary detector can be a fallback, but should not claim semantic chorus recognition.

### 4. Produce supported musical descriptions

Retire GTZAN top-1 as the authoritative genre. Until replacement is validated, retain the ranking and show ambiguity or abstain. Never convert an uncalibrated softmax score into a user-facing certainty percentage.

Build a multi-label style schema: broad genre and subgenre candidates, multiple instruments, vocal delivery, production, energy and measured rhythm features. Sample representative interior sections and transitions, omit silence, and retain per-excerpt scores instead of averaging away disagreement. Reuse text embeddings for a versioned descriptor vocabulary, and reuse each audio embedding across categories. Select multiple instruments when independently supported; permit no selection.

CLAP can remain an evidence source, but should not write unrestricted prose. Compose a compact description only from accepted attributes; ambiguous genre should not invalidate supported instrumentation. Rank consistent evidence across excerpts and make per-category disagreement explicit. Estimate BPM from beat tracking with a half/double-tempo ambiguity check; do not derive an exact BPM from a semantic CLAP phrase.

Evaluate music-trained CLAP against the present checkpoint rather than assuming bigger is better. There is a reported near-constant-text-embedding issue for `laion/larger_clap_music` [8]; verify embedding variation, cross-modal retrieval and the exact checkpoint revision before adopting it. This report is a validation warning, not proof that every music CLAP checkpoint is broken.

Music Flamingo is relevant for richer captions but is not the baseline choice for this 16 GiB app: its model card describes an 8B model optimized for NVIDIA hardware and a noncommercial license [9]. That raises concrete deployment and distribution constraints. A small text model could polish validated attributes, but cannot recover acoustic facts that were never detected.

### 5. Bound resource use

One heavy model at a time, including the YuE generation worker. Process stems/windows incrementally; reuse separation, spectrograms, text embeddings and results. Release device allocations between stages and handle allocation failure explicitly. Support cancellation at window boundaries, atomic partial results and offline operation after installation. A fast/accurate choice must state extra downloads and cost; do not silently download another large model during Analyze.

## Verification and acceptance

Use synthetic tests for actual API paths, not just mocks: long-form token/timestamp offsets, empty/no-vocal windows, cache boundaries, sample-rate conversion, stereo channel preservation, interruption/restart, partial downloads and cancellation. Cover punctuation, Unicode, genuine repeated choruses, overlapping phrases and segment-boundary deduplication. Test descriptors with ambiguous/contradictory scores, silent excerpts and multiple simultaneous instruments. Numerical parity checks are needed before choosing an MLX port.

A generated tone or random-weight model cannot establish singing accuracy. Keep that distinction explicit: respecting the current synthetic-only constraint, test robustness and report musical quality as unverified. A future separately authorized headless benchmark (still no app UI) should compare:

- baseline vs vocal-boundary segmentation, mix vs vocals, turbo vs large-v3;
- lyric WER/CER plus insertion/deletion counts, including ad-libs;
- word timing error and recovered/failed alignment rate;
- section boundary F1 and label accuracy;
- multi-label style precision and abstention coverage;
- wall time, real-time factor and peak memory on this host.

Use fixed, held-out references (e.g. Jam-ALT/MUSDB-ALT subject to their dataset terms) and keep the user's example as a regression case, not a hardcoded correction. No numerical accuracy/speed target should be claimed achieved before measurement.

## Order of work

1. Per-segment diagnostics, per-stage persistence, genre uncertainty and non-destructive Apply behavior.
2. Isolated Apple-accelerated transcription worker, vocal-boundary segmentation and independent alignment.
3. Acoustic structure model and timestamp-to-section mapping, reusing stems.
4. Multi-label, multi-section style evidence and concise supported descriptions.
5. Synthetic regression gates; separately measured quality before changing accuracy claims or publishing another release.
